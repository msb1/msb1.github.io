Notes on a Reference RAG Implementation

August 30, 2026

Retrieval-augmented generation is often presented as a short recipe: embed documents, retrieve a few chunks, and ask a model to answer from them. rag-bench is deliberately more complete. It is a reference implementation for measuring an end-to-end RAG system against the Open RAG Benchmark: 1,000 arXiv PDFs and 3,045 question-answer pairs, including text, table, and image-oriented questions.

The project makes the whole path observable. PDFs are converted to Markdown, indexed in Qdrant, retrieved with dense and sparse signals, reranked locally, used to generate a grounded answer, then evaluated and analyzed as a record-level dataset.

System shape

The workflow is intentionally staged:

  1. convert.py reads PDFs from S3-compatible storage and converts them to Markdown with PyMuPDF/PyMuPDF4LLM.
  2. chunker.py creates structured chunks and hybrid Qdrant vectors.
  3. rag.py performs query expansion, retrieval, reranking, context assembly, and answer generation.
  4. eval.py and evaluate.py apply custom LLM-as-a-judge metrics.
  5. analyze.py produces score distributions and focused failure sets.

Local OpenAI-compatible endpoints provide embeddings, generation, and evaluation. Qdrant provides the vector store, while MinIO/RustFS-style object storage supplies the source documents. A small custom embeddings adapter sends batches directly to the local endpoint, avoiding assumptions in the standard client’s pre-tokenization path.

PDF preparation and indexing

PDFs are converted into Markdown before chunking so the system can retain useful structure. The chunking pass strips terminal reference sections, splits first by Markdown headings and then with a recursive 512-character splitter with 51-character overlap, and rejects short page fragments, isolated images, and math-heavy scraps with too little language content.

Tables are extracted before text splitting, replaced with placement markers, and stored as raw table metadata on the neighboring chunk. This retains the actual table rather than replacing it with an LLM summary. Each final chunk gets a readable logical identifier and a deterministic UUIDv5, making repeated indexing auditable. Qdrant stores a dense embedding alongside FastEmbed BM25 sparse vectors for hybrid retrieval.

RAG Fusion and grounded generation

For each question, a low-temperature model produces three alternate phrasings. Every variation retrieves up to twelve hybrid candidates. The pipeline deduplicates candidates by content, then sends the remaining pool in a single request to a local GPU-hosted jina-reranker-v3.5 FastAPI service. The best five documents become the context. If the reranker is unavailable, it falls back to the original order so a long benchmark run can continue.

Selected chunks have their associated tables cleaned and restored before context is formatted as numbered source blocks. The generation prompt permits only retrieved facts, forbids supplementing with training knowledge, and requires an explicit abstention when the answer is absent. Every run writes the question, answer, final contexts, and ground truth to JSONL, while progress.json supports resuming interrupted runs.

Custom evaluation in lieu of a fixed RAGAS call

rag-bench does not treat RAGAS as a black-box call. It implements an embedding-free, local LLM-as-a-judge protocol with five explicit metrics. Faithfulness extracts independent answer claims and verifies each against context. Relevancy reconstructs the question implied by the answer and compares its intent to the original. Context recall decomposes the ground truth into facts and checks for each in retrieved evidence. Context precision judges each context sentence for usefulness. Answer correctness classifies facts as TP, FP, and FN in JSON and calculates TP / (TP + 0.5 × (FP + FN)).

That decomposition makes scores diagnosable. A poor faithfulness score points to unsupported claims; low recall identifies ground-truth facts that retrieval missed; low precision exposes irrelevant context. The correctness metric separates omissions from unsupported additions. It also has a semantic-score fallback when a local judge returns malformed JSON.

This is a better evaluation fit than a fixed RAGAS abstraction when the aim is to improve this specific system: the project can tune the fact definition, rubric, evidence granularity, prompts, judge model, and thresholds while retaining every intermediate judgment. It also avoids adding embedding similarity solely for the relevancy calculation. The trade-off is intentional, not absolute: RAGAS remains valuable for standardized comparisons. A custom evaluator earns its value when prompts and models are versioned, outputs are human-sampled, and repeat runs measure judge variance.

Implementation detail: data, chunks, and retrieval

The project deliberately separates durable artifacts. Benchmark query IDs resolve to query text in queries.json and expected answers in answers.json. Generation appends one self-contained record per line to results/results.jsonl: question, answer, final reranked contexts, and ground truth. Evaluation can therefore be rerun with a different judge prompt or model without paying to re-index or regenerate answers. The final score records are written separately to results/output.jsonl.

The converter pages through an S3-compatible PDF prefix, streams every object into PyMuPDF, converts it using PyMuPDF4LLM, and writes Markdown to the matching markdown/ prefix. The chunker processes each Markdown file independently. It removes references, extracts tables to numbered markers, splits first on headings and then at 512 characters with 51-character overlap, removes low-value fragments, and restores table associations in metadata. Each kept chunk receives a readable logical ID and a UUIDv5 derived from it, so an index can be reproduced and audited across runs.

Retrieval is a LangChain expression pipeline. Three alternate query wordings each retrieve 12 candidates from Qdrant hybrid mode, which combines dense vectors with FastEmbed BM25 sparse vectors. Candidates are deduplicated by exact text. The original question and all remaining texts then travel in one request to the GPU-hosted Jina reranker; it returns indices and scores, and the best five documents are reconstructed as LangChain documents. The pipeline captures these post-rerank contexts—not the wider candidate pool—so evaluation measures exactly what the answer model saw. A 15-second timeout and fallback to original order keep long runs moving when the reranker is unavailable.

Context is rendered as numbered source blocks. Associated tables are cleaned for repeated headers, continuation banners, duplicate separators, line breaks, and escaped entities before being appended to the selected text. The answer prompt accepts only retrieved facts, forbids training-knowledge supplementation, and provides a fixed abstention response. After every generated answer, JSONL is appended and progress.json is updated, allowing a stopped run to restart from the next benchmark record.

Implementation detail: custom metric calculations

Faithfulness is a two-pass calculation: the judge extracts independent claims from the answer, then receives one YES/NO evidence-verification request for each claim. The score is supported claims divided by all claims. Context recall mirrors that procedure on the ground-truth facts, making it possible to tell whether missing content was a retrieval failure rather than a generation failure.

Answer relevancy asks the judge to reconstruct the question the answer seems to address, then scores the semantic-intent match with the original question. Context precision splits the formatted context into sentences and asks whether each sentence is useful for the question given the known answer. Answer correctness requests a JSON list of true positives, false positives, and false negatives, then calculates TP / (TP + 0.5 × (FP + FN)). If the JSON is malformed after fence cleanup, it falls back to a direct semantic correctness score so one formatting error cannot end a batch.

All judge calls use the local OpenAI-compatible chat endpoint at temperature zero with a 30-second timeout. The design is more adaptable than a fixed RAGAS call because every fact definition, rubric, prompt, judge model, threshold, and evidence granularity can be changed and inspected. It is not a claim that custom judging is universally more accurate: the evaluator should version its prompts/models, sample outputs for human review, record parse and transport failures explicitly, and check score variance across repeated runs.

Analysis closes the loop

The analysis stage reports means, minima, maxima, and standard deviations, and renders both an average-score chart and distribution box plots. More importantly, it exports hallucinations.jsonl for faithfulness below 0.30 and retrieval_misses.jsonl for context recall below 0.30. Those are severe triage thresholds, not definitions of success. Each exported row retains the question, answer, ground truth, contexts, and scores, allowing review to trace a failure through conversion, chunking, hybrid retrieval, reranking, and generation.

Reproducing the run

python -m src.convert
python -m src.chunker
python -m src.rag
python -m src.eval
python -m src.analyze

The reference value of rag-bench is not that it removes uncertainty from RAG. It preserves evidence at each stage so that uncertainty can be measured, inspected, and improved.
